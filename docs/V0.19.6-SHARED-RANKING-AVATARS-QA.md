# V0.19.6 — Shared Ranking Avatars QA

## Requirement

All users viewing Ranking should see each other's selected Soft 3D avatars.

## Design decision

Avatar data is not copied into `exam_attempts`.

A separate public profile table is used:

`ranking_profiles(player_id, avatar_id, updated_at)`

Reason:
- avatar changes do not require another exam attempt
- historical attempts immediately inherit the current avatar
- attempt/ranking scoring schemas remain clean
- no category/gender field is needed

## Client sync

`online.js` adds:

- `syncRankingAvatarProfile(playerId, avatarId)`
- `fetchRankingProfiles(playerIds)`

The client allowlists all 16 production avatar IDs.

Invalid avatar IDs are rejected before a network request.

## Ranking rendering

`app.js` maintains:

`state.rankingAvatarMap`

Before rendering:
- exam ranking fetches profile mappings for board player IDs
- aggregate ranking fetches profile mappings for result-board player IDs

`rankingAvatarHtml()` then resolves:
1. shared Supabase avatar
2. own local avatar as immediate fallback
3. initials

This applies to:
- regular leaderboard rows
- aggregate/Official Total Grades rows
- Top-3 podium

## Automatic profile sync

Current avatar is synced:
- on app startup for existing avatar users
- after first avatar selection
- after returning-user required rollout
- after ranked identity onboarding
- after Change Avatar

Sync failures are non-blocking.

## Privacy

Shared table stores only:
- player_id
- avatar_id
- updated_at

Not stored:
- gender/category
- email
- answers
- Analytics visitor ID

`exam_attempts` remains unchanged.

## Automated tests

Pre-Deploy PASS verifies:
- every row can resolve avatar by player_id
- separate profile fetch/upsert implementation exists
- SQL migration exists and enables RLS
- avatar allowlist exists in client and database
- no gender/category in ranking profile schema/API block
- existing attempt payload has no avatar field
- all prior platform regression suites pass

Direct online module QA:
- UPSERT payload — PASS
- profile fetch/map — PASS
- invalid avatar allowlist rejection — PASS

## Deployment dependency

The code package alone is not enough.

Run:

`supabase/RANKING-AVATARS-V0.19.6.sql`

before V0.19.6 goes LIVE.

## LIVE acceptance test

Use two different browsers/devices.

Each user chooses an avatar and opens the updated platform.

Then verify each browser can see the other learner's avatar in Ranking.

This LIVE two-user test cannot be fully completed offline because it depends on the real Supabase table.
