### PR 2B — Security and Storage Hardening

Review Stage 1 candidates by data flow, prioritizing learner-controlled, backup-controlled, and network-controlled values. Presence of `innerHTML`, `localStorage`, `fetch`, or an external URL is not itself a defect.

The review order is:

1. Backup import validation and backup-rendered values.
2. Learner identity/avatar and user-visible error/status values.
3. Optional analytics and ranking responses.
4. Exam context, mistakes, update-manager, and PL-300 review markup.
5. Early theme restoration and external link/font policy.

For each candidate, record source, transformations, sink, trust boundary, failure behavior, and disposition. A runtime fix is permitted only after a failing regression reproduces unsafe or incompatible behavior. Prefer existing escaping, safe-storage, and validation adapters; do not introduce a new storage schema or sanitize trusted generated markup twice.

Optional analytics/ranking failures must remain isolated from local study and exams. Malformed storage or backup input must fail closed without destroying recoverable learner state.

### PR 2C — Proven Cleanup

Evaluate the eight generated-metadata candidates and any additional orphan candidates reported by the deterministic inventory. A file may be deleted only when all of the following are proven:

1. No literal or constructed runtime, registry, manifest, test, tool, workflow, or documentation consumer requires it.
2. Directory enumeration and dynamic-path use have been checked.
3. The file is not an authoritative source, regeneration input, test fixture, or historical/release evidence.
4. Generated outputs have a known generator, complete inputs, deterministic command, and durable replacement or regeneration path.
5. Removal passes focused tests, reference audit, protected baseline, full regression, PL-300 509 checks, local HTTP smoke, performance, and pre-deploy.

Every deletion is recorded in a manifest containing path, classification, byte size, evidence, replacement/regeneration path, deletion commit, and rollback command. Candidates without complete proof remain and receive an explicit `keep` disposition. Zero deletions is a valid result.

### PR 2D — Final Acceptance and Evidence Closure

Run the complete browser and deployment-oriented acceptance matrix on a clean final candidate without changing runtime behavior merely to satisfy incomplete infrastructure coverage.

Required journeys:

- first and returning learner, avatar, track, theme, reload;
- all primary routes;
- Excel, SQL, and Python study/practice/full-track flows;
- Junior and Professional Official QBank;
- PL-300 509 landing, domain/section/part, answer lock, delayed retry, end-of-part review, and Review & Solve Again;
- timer, resume, navigator, MARK, result, retry, mistakes, and ranking boundaries;
- valid backup/restore and malformed-input rejection;
- keyboard focus, dialogs, RTL/LTR rendering, overflow, desktop/mobile, and light/dark;
- optional analytics/ranking failure isolation where browser tooling supports interception;
- GitHub Pages subpath asset loading and source/build artifact parity.

Any confirmed bug returns to a bounded fix PR with a failing regression first. The final acceptance PR contains evidence and release documentation only unless a separately approved bounded fix is required.

## Protected Boundaries

Stage 2 must not change:

- `official-qbank/`, `question-banks/`, `exams/`, or protected curriculum/assessment payloads under `data/`;
- PL-300 source/master banks, classifications, answer corrections, question assets, or the 509 full-ranked index;
- learner identity, progress, attempts, first-pass history, mastery, mistakes, marks, resume, or backup compatibility contracts;
- scoring, ranking, timer-fairness, or Supabase transport schemas;
- the 450 KiB startup gzip budget.

Release metadata, cache queries, guard tests, evidence reports, and proven unused files may change within their owning PR.

## Testing Strategy

Every behavioral fix follows red-green-refactor TDD. Every PR runs its focused tests plus:

1. JSON and JS/MJS syntax checks.
2. Local reference audit.
3. Security/privacy audit.
4. Protected-payload baseline check.
5. PL-300 exhaustive audit and 509/509 index check.
6. Full Node regression.
7. Startup performance at the unchanged 450 KiB limit.
8. Pre-deploy.
9. Local GitHub Pages-subpath HTTP smoke.
10. Exact-head PR CI.

Browser evidence is reported separately from automated evidence. Unsupported or interrupted browser rows remain pending and are never converted into passes.

## Error Handling and Rollback

- Cache changes are atomic: all V0.22.8 identities move together or the PR does not merge.
- Security/storage fixes fail closed and preserve recoverable local data.
- Optional services cannot block local learning or assessment flows.
- Each cleanup deletion is isolated enough to revert from its recorded commit.
- A high-risk finding that expands scope becomes its own bounded PR.
- Every PR stops before merge; deployment and post-deploy verification require Ahmed Khaled's explicit approval.

## Acceptance Criteria

Stage 2 is complete only when:

- V0.22.8 identity is consistent and the reference audit reports zero current-release query mismatches;
- confirmed unsafe data flows are regression-tested and fixed, while review-only occurrences have documented dispositions;
- every removed file has complete deletion proof and rollback evidence;
- protected payloads and learner contracts remain unchanged;
- PL-300 remains 509/509 and all permanent gates pass on each exact final SHA;
- the complete browser matrix is either passed or truthfully lists a concrete remaining infrastructure blocker;
- GitHub Pages serves the approved V0.22.8 artifact after merge authorization;
- no temporary workflow, patch scaffold, diagnostic artifact, or unrelated refactor is shipped.

## Explicit Non-goals

- No visual redesign or new learning feature.
- No question, answer, explanation, scoring, ranking, or curriculum rewrite.
- No speculative sanitization, storage migration, dependency replacement, or large-file refactor.
- No deletion based on age, naming, apparent duplication, or an incomplete reference search.
- No merge or deployment without explicit approval.
