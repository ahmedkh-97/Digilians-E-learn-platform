# V0.22.8 Platform Hardening Stage 1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Establish a trustworthy V0.22.7 whole-platform baseline, permanent audit guardrails, consistent release/CI metadata, and an evidence-backed findings report without deleting files or changing protected production data.

**Architecture:** Stage 1 adds small read-only Node audit tools with focused tests, then connects only stable pass/fail contracts to the permanent pre-deploy workflow. Repository classification and candidate discovery remain reporting functions; they never delete or rewrite files. The final Stage 1 report becomes the source of truth for a separately written Stage 2 cleanup plan.

**Tech Stack:** Static HTML/CSS, browser-native ES modules, Node.js 22 built-ins (`node:test`, `fs`, `path`, `crypto`, `child_process`), GitHub Actions, GitHub Pages, JSON and Markdown evidence.

**Spec:** `docs/development/V0.22.8-PLATFORM-HARDENING-DESIGN.md`

## Global Constraints

- Baseline is V0.22.7 at commit `af59e73f7a51d2745430a1de2db298d0f97af728`.
- Stage 1 performs no repository-file deletion.
- Do not rewrite `official-qbank/`, `question-banks/`, `exams/`, curriculum/assessment payloads under `data/`, or PL-300 source/master/index assets.
- Do not change learner storage, scoring, mastery, ranking, timer, resume, analytics, or Supabase contracts.
- Keep the startup gzip estimate at or below 450 KB.
- Audit and report uncertain files; never classify uncertainty as permission to delete.
- Use regression-first changes and commit each independently reviewable task.
- Run all permanent gates on the exact clean head before opening the Stage 1 pull request.
- Stop before merge and require Ahmed Khaled's explicit approval.
- Store planning and audit documents under `docs/development/` or `docs/releases/`; never create `docs/superpowers/` because the repository cleanliness contract forbids shipping it.

- [ ] **Step 4: Implement the read-only inventory module**

Implement `tools/platform-inventory.mjs` using only Node built-ins. Requirements:

```js
export function classifyPath(repoPath,policy){
  const matches=policy.rules.filter(rule=>new RegExp(rule.pattern).test(repoPath));
  return matches[0]?.classification||'unclassified';
}

export function sha256(buffer){
  return createHash('sha256').update(buffer).digest('hex');
}
```

`buildInventory()` must:

1. obtain tracked paths from `git ls-files -z` when `paths` is omitted;
2. normalize separators to `/` and sort paths lexically;
3. record `{path, classification, size, sha256}` for each file;
4. aggregate count and bytes by classification;
5. emit `unclassified` paths separately;
6. include `baselineVersion` from `VERSION.txt` and `baselineSha` from `git rev-parse HEAD`;
7. write only when the CLI receives `--write <repo-relative-path>`.

It must also copy `generatedArtifacts` into a provenance section and produce `generatedReviewCandidates` for files described as generated by their own metadata or documentation but not yet declared in policy. These candidates are reviewed in Task 8; they are not deleted or treated as reproducible until their generator, inputs, and check command are verified.

Reject absolute output paths and output paths outside `docs/releases/` so the audit cannot overwrite arbitrary repository content.
