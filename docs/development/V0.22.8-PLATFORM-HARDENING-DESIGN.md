# V0.22.8 Platform Hardening and Evidence-Based Cleanup Design

## Status

- Design baseline: `main` at V0.22.7 (`af59e73f7a51d2745430a1de2db298d0f97af728`)
- Scope: whole-platform audit, targeted hardening, and evidence-based repository cleanup
- Delivery model: two reviewable pull requests, each stopped before merge
- Core rule: no assessment, curriculum, learner-history, scoring, or ranking data is changed by cleanup work

## Purpose

V0.22.8 will make the Digilians E-Learn Platform easier to trust, test, maintain, and deploy without redesigning the frozen learning and assessment core. The work must identify real defects, prove whether cleanup candidates are unused, fix only confirmed problems, and leave a repeatable audit trail.

Success means the platform remains behaviorally compatible while its release metadata, CI coverage, runtime integrity, accessibility, security posture, performance budgets, documentation, and repository contents are internally consistent.

## Non-goals

- No visual redesign or new learning feature.
- No rewriting of question banks, explanations, answers, classifications, or curriculum payloads.
- No scoring, mastery, ranking, timer, resume, or storage-schema redesign.
- No speculative refactor of large runtime files solely to make them smaller or cleaner.
- No deletion based only on age, filename, apparent duplication, or lack of a direct runtime reference.
- No raising of the 450 KB startup gzip budget to make a gate pass.

## Delivery Strategy

### Stage 1 — Audit and Guardrails

Stage 1 establishes a trustworthy baseline and fixes only the infrastructure needed to measure the platform correctly.

Deliverables:

1. A machine-readable repository inventory covering runtime, source, generated, historical evidence, tests, documentation, and tooling.
2. A reference/dependency audit for HTML, JavaScript, CSS, JSON, images, manifests, registries, tests, tools, documentation links, and CI workflows.
3. Release-identity consistency across `VERSION.txt`, `index.html`, cache-busted asset references, runtime build metadata, changelog, README, release documentation, and workflow labels.
4. CI trigger and contract review so pull requests and the accepted post-merge branch state are both validated by the intended permanent gates.
5. Guard tests for protected payload hashes/counts, release identity, generated-file provenance, broken local references, storage compatibility, and workspace cleanliness.
6. A baseline report containing test totals, bank counts, file counts and sizes, startup payload, critical-route smoke results, and known findings.

Stage 1 must not delete repository files or change production assessment content.

### Stage 2 — Proven Cleanup and Confirmed Fixes

Stage 2 acts only on findings supported by Stage 1 evidence.

Deliverables:

1. Regression tests for every confirmed behavior defect before its fix.
2. Minimal fixes for confirmed runtime, UX, accessibility, security, portability, or documentation defects.
3. Deletion of files that satisfy the complete deletion policy below.
4. A deletion manifest recording path, category, size, evidence, replacement or regeneration path, and rollback commit.
5. Updated release metadata for V0.22.8 only after the final change set is known.
6. Full clean-head verification, GitHub Pages deployment verification after merge approval, and a post-deploy report.

## Protected Boundaries

The following areas are immutable during cleanup unless a separately identified defect requires an explicitly approved content/data change:

- `official-qbank/`
- `question-banks/`
- `exams/`
- curriculum and assessment payloads under `data/`
- PL-300 source banks, master banks, question assets, classifications, corrections, and the 509 full-ranked index
- learner identity, progress, attempts, first-pass history, mastery, mistakes, marks, resume state, and backup/restore compatibility
- ranking and scoring rules
- analytics and Supabase data contracts

Release-only metadata such as `VERSION.txt`, `data/changelog.json`, README status, cache identity, CI labels, and release reports may change when required for consistency.

Protected payloads will be compared against the V0.22.7 baseline by path, record count, stable identifiers, and content hash where practical.

## Repository Classification Model

Every tracked file must receive one primary classification:

| Classification | Meaning | Cleanup treatment |
| --- | --- | --- |
| Runtime | Loaded or requested by the deployed application | Keep unless replaced and all consumers are migrated |
| Runtime data | Production registry, bank, config, manifest, or payload | Protected; do not rewrite during cleanup |
| Source | Authoritative input used to produce runtime or evidence | Keep unless a verified durable source exists elsewhere |
| Generated | Reproducible output with a documented generator and inputs | Candidate only when regeneration is proven and consumers do not require it |
| Test fixture | Required by an automated validation contract | Keep unless the owning test is safely replaced |
| Tooling | Used for production, validation, ingestion, repair, or release | Keep when invocation or provenance is active/documented |
| Documentation | Current operational, production, source, or release evidence | Keep, consolidate, or correct based on documented purpose |
| Historical evidence | Supports traceability but not current runtime | Keep by default; archive/consolidate only with explicit evidence |
| Orphan candidate | No verified consumer, generator role, or evidence purpose | Eligible for the deletion proof process |

Apparent duplicates such as draft/master banks, Markdown/HTML pairs, source-review assets, and audit reports are not orphans until their production or evidence role is resolved.

## Deletion Proof Policy

A file may be deleted only when all applicable checks pass:

1. No runtime, HTML, CSS, JavaScript, JSON, registry, manifest, test, tool, workflow, or documentation reference requires it.
2. Dynamic path construction and directory enumeration have been checked, not only literal string references.
3. It is not an authoritative source, regeneration input, audit artifact, release evidence, or required test fixture.
4. If generated, its generator, inputs, command, and deterministic output are documented and verified.
5. Removing it passes targeted tests, the full Node regression, pre-deploy, path portability, integrity audits, and local HTTP smoke.
6. Its removal is recorded in the deletion manifest with a rollback reference.

Uncertain files remain in the repository and are reported as unresolved; uncertainty is never converted into permission to delete.

## Audit Coverage

### Release and Deployment Integrity

- Match release version and build identity across all authoritative surfaces.
- Detect stale release names, branch filters, cache keys, and documentation claims.
- Verify GitHub Pages subpath portability and Jekyll/build-artifact differences.
- Compare the source tree, clean package, served package, and deployed artifact for expected runtime files.
- Confirm cache invalidation and update-manager behavior without discarding learner data.

### Runtime and User Journeys

Critical journeys include:

- first visit, returning learner identity, avatar selection, and theme restoration
- Home, Learn, Official QBank, Exams, Voucher, My Mistakes, Ranking, backup, and restore navigation
- Excel, SQL, and Python study/practice/full-track flows
- Junior and Professional Official QBank flows
- PL-300 landing, domain/section/part selection, all 509 mode, immediate feedback, end-of-part review, smart retry, and review-and-solve-again
- timer, pause/resume, answer lock, navigator, MARK, unanswered handling, result calculation, retry, mistakes recovery, and rank submission
- refresh, back/forward navigation, direct deep links, interrupted loading, missing optional network services, and offline/local-first fallback

### Data Integrity

- Validate JSON syntax and required schema fields.
- Verify registry-to-file linkage and referenced assets.
- Check stable and unique question IDs within their defined scopes.
- Verify expected production counts and section/domain coverage.
- Detect unintended cross-bank duplication without modifying legitimate reused source concepts.
- Verify correct-answer indexes, native interaction structures, explanation availability, and code rendering contracts.
- Preserve the PL-300 509/509 index and its validated-concept mastery model.

### UX and Accessibility

- Desktop and mobile layouts at representative widths.
- Light and dark themes, Arabic RTL and English/code LTR boundaries.
- Keyboard-only operation, visible focus, dialog behavior, semantic controls, labels, and live feedback.
- Contrast, readable text sizing, overflow, long code, long choices, dropdowns, tables, and error messages.
- Consistent context labels so the learner always knows the track, bank, domain, section, part, and question position.

### Security and Privacy

- Search for committed credentials, tokens, private endpoints, unsafe debug output, and unintended personal data.
- Review Supabase/client configuration, least-privilege assumptions, failure behavior, and optional-service isolation.
- Review unsafe HTML insertion, URL handling, external links, backup/restore validation, storage parsing, and error reporting boundaries.
- Confirm analytics and health reporting do not expose learner answers or identity beyond their documented contracts.

### Performance and Reliability

- Keep the startup gzip estimate at or below 450 KB.
- Measure startup request count, critical assets, largest runtime files, duplicate downloads, and unnecessary eager loading.
- Detect missing assets, broken local links, syntax errors, unhandled promise rejections, console errors, and stalled loading states.
- Preserve graceful operation when analytics, ranking sync, or other optional network services are unavailable.

## Testing and Evidence Model

The following gates apply to each stage's clean final SHA:

1. Focused tests for the changed contracts.
2. Syntax and JSON validation.
3. Protected payload count/hash comparison against V0.22.7.
4. PL-300 exhaustive 509 audit.
5. Full-ranked index check confirming 509/509.
6. Full Node regression.
7. Startup performance gate with the existing 450 KB limit.
8. Pre-deploy gate.
9. Local HTTP smoke using the GitHub Pages subpath model.
10. Browser acceptance matrix for representative desktop/mobile and light/dark combinations.
11. Clean-package re-verification when packaging is part of the release.
12. PR CI on the exact head SHA.

After an approved merge, GitHub Pages build/deploy status and the served production artifact are verified separately. A source-only green run is not treated as live-site proof.

## Error Handling and Rollback

- Audit scripts must report uncertain classifications without deleting or rewriting files.
- Fixes must fail closed around malformed learner backups or corrupted storage while preserving recoverable data.
- Optional online integrations must fail independently and leave local study/exam behavior usable.
- Every cleanup commit must be reversible without reconstructing deleted content from memory.
- Each pull request stops before merge and includes its exact clean SHA, evidence, known limitations, and rollback point.
- No deployment or merge occurs without Ahmed Khaled's explicit approval.

## Pull Request Structure

### PR 1 — Audit and Guardrails

- Inventory and provenance tooling
- release/README/changelog/workflow consistency
- missing integrity and compatibility guards
- baseline and findings report
- no repository-file deletion and no production assessment-data change

### PR 2 — V0.22.8 Proven Cleanup and Hardening

- regression-tested confirmed fixes
- evidence-backed deletions
- deletion manifest
- release identity and changelog update
- complete clean-head and pre-deploy evidence

If Stage 1 reveals a high-risk bug whose safe correction would materially expand the second PR, it becomes a separate bounded PR instead of being hidden inside cleanup work.

## Acceptance Criteria

The initiative is complete only when:

- all permanent validation gates pass on the exact final SHA;
- the production banks and protected learner contracts remain unchanged except for separately approved fixes;
- the 509 PL-300 questions remain reachable, auditable, and correctly indexed;
- README, release identity, changelog, cache identity, workflow names, and deployed build agree;
- every deleted file has complete evidence and rollback information;
- critical user journeys pass browser acceptance without console errors;
- startup remains within the existing 450 KB gzip budget;
- GitHub Pages serves the expected V0.22.8 artifact after an explicitly approved merge;
- both pull requests contain no temporary diagnostic workflow, patch scaffold, generated junk, or unrelated change.

## Initial Known Findings to Validate

The design review identified these as audit findings, not pre-approved fixes:

- `VERSION.txt` reports V0.22.7 while README release text still reports V0.22.2.
- The permanent workflow title and focused gate labels still reference V0.22.6.
- The workflow's push branch filter names an older feature branch, so accepted post-merge validation coverage must be verified.
- The repository contains source, draft, master, review, audit, and generated PL-300 artifacts whose distinct roles must be documented before cleanup.
- Documentation policy and retained HTML documentation mirrors require a purpose-level consistency check rather than filename-based deletion.

These findings must be reproduced and classified during Stage 1 before any corrective change is made.
